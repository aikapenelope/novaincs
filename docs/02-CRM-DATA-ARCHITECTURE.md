## 1. Micro-CRM: Value Delivered to the Merchant

The CRM is not a feature — it is the **core value engine** of Nova. Everything else (catalog, payments, inventory) feeds data into the CRM, and the CRM feeds intelligence back out to the merchant. The merchant never "uses the CRM" directly. They experience its value as **insights, suggestions, and automated actions** that appear naturally in their workflow.

### 1.1 What the Merchant Sees (Value Surfaces)

The CRM manifests through five concrete value surfaces that the merchant interacts with daily:

#### Surface 1: The Customer Card

Every person who interacts with the merchant's catalog or WhatsApp gets an automatic profile. The merchant never fills out a form. The system builds the card from observed behavior.

| Field | Source | Auto/Manual |
|---|---|---|
| Name | WhatsApp contact name, or manual entry | Auto + editable |
| Phone | WhatsApp number or checkout form | Auto |
| Delivery zone | Address from orders, or GPS from catalog visits | Auto + editable |
| Preferred payment method | Most-used method across orders | Auto |
| Total lifetime value ($) | Sum of all confirmed orders | Auto |
| Total orders | Count of confirmed orders | Auto |
| Average order value | Lifetime value / total orders | Auto |
| Last purchase date | Most recent confirmed order | Auto |
| Days since last purchase | Today - last purchase date | Auto |
| RFM Score | Composite of Recency, Frequency, Monetary | Auto |
| Tags | VIP, Frequent, At Risk, New, Window Shopper, Custom | Auto + manual |
| Favorite categories | Top 3 product categories by purchase volume | Auto |
| Favorite products | Top 5 products by purchase frequency | Auto |
| WhatsApp interaction count | Messages sent/received (not content, just count) | Auto |
| Catalog visit count | Number of times they visited the public catalog | Auto |
| Last catalog visit | Timestamp of most recent catalog page view | Auto |
| Products viewed (last 30d) | List of products they looked at | Auto |
| Cart abandonment count | Times they added to cart but didn't complete | Auto |
| Merchant notes | Free-text notes the merchant adds | Manual |
| Custom tags | Merchant-defined labels ("wholesale", "friend", etc.) | Manual |

#### Surface 4: Customer Segments (Auto-Generated)

The system automatically creates and maintains segments. The merchant doesn't configure rules — the system does it based on RFM analysis and behavioral patterns.

| Segment | Definition | Typical Size | Suggested Action |
|---|---|---|---|
| **VIP** | Top 20% by monetary value AND frequency >= 3 orders/month | 5-10% of base | Exclusive offers, early access, personal attention |

| **Promising** | Recent first purchase with high order value | 5-10% | Welcome sequence, second-purchase incentive |

| **Window Shopper** | 5+ catalog visits, 0 purchases | 15-25% | First-purchase incentive, WhatsApp outreach |
| **New** | First interaction in last 7 days | Variable | Welcome message, catalog highlights |
| **One-Timer** | Exactly 1 purchase, 30+ days ago | 20-30% | Second-purchase incentive |

### 1.2 RFM Scoring Model

RFM (Recency, Frequency, Monetary) is the backbone of the CRM intelligence. Each customer gets a score from 1-5 on each dimension.

**Recency** (days since last purchase):
| Score | Days Since Last Purchase |
|---|---|
| 5 | 0-7 days |
| 4 | 8-14 days |
| 3 | 15-30 days |
| 2 | 31-60 days |
| 1 | 60+ days |

**Frequency** (orders in last 90 days):
| Score | Orders in 90 Days |
|---|---|
| 5 | 10+ |
| 4 | 6-9 |
| 3 | 3-5 |
| 2 | 2 |
| 1 | 0-1 |

**Monetary** (total spend in last 90 days):
| Score | Spend (USD) |
|---|---|
| 5 | Top 10% of customers |
| 4 | Top 10-25% |
| 3 | Top 25-50% |
| 2 | Top 50-75% |
| 1 | Bottom 25% |

The thresholds are **per-merchant**, not global. A bakery's "high frequency" is different from a shoe store's. The system calibrates automatically based on each merchant's data distribution after the first 30 days of operation.

**Composite Score**: The three scores combine into a segment assignment. For example:
- RFM 555 = "Champion" (best customer)
- RFM 511 = "New high-value" (just bought a lot, first time)
- RFM 155 = "Can't lose them" (used to be great, hasn't bought recently)
- RFM 111 = "Lost" (low on everything)

### 1.3 Accounts Receivable Tracking

Every order has a payment status lifecycle:

```
CREATED -> PAYMENT_PENDING -> SCREENSHOT_UPLOADED -> VERIFYING -> VERIFIED -> COMPLETED
                                                  -> REJECTED -> PAYMENT_PENDING (retry)
```

The Finance Agent tracks:
- **Total accounts receivable**: Sum of all orders in PAYMENT_PENDING or VERIFYING status
- **Aging**: How many days each receivable has been pending
- **Per-customer receivable**: Which customers owe money and how much
- **Auto-reminders**: After X days (configurable), the system suggests sending a payment reminder via WhatsApp

The merchant sees this as a simple card:

```
CUENTAS POR COBRAR: $234
- Juan Perez: $45 (3 dias) [Recordar]
- Ana Lopez: $89 (1 dia) [Recordar]
- Pedro Gomez: $100 (hoy) [Verificar pago]
```

## 2. Data Ingestion Architecture

### 2.1 The Three Data Streams

Nova ingests data from three distinct streams, each with different characteristics:

#### Stream 1: Behavioral Data (High Volume, Real-Time)

This is the most valuable and unique data Nova collects. It comes from customer interactions with the catalog and WhatsApp.

| Event | Source | Volume | Latency Requirement |
|---|---|---|---|
| Catalog page view | Customer PWA (analytics pixel) | High (100s/day per merchant) | Near real-time (< 5 sec) |
| Product view | Customer PWA | High | Near real-time |
| Add to cart | Customer PWA | Medium | Real-time (< 1 sec) |
| Cart abandonment | Customer PWA (timeout) | Medium | Near real-time |
| WhatsApp message received | WhatsApp Cloud API webhook | Medium | Real-time |
| WhatsApp message read | WhatsApp Cloud API webhook | Medium | Near real-time |
| Catalog shared (link click) | Customer PWA (referral tracking) | Low-Medium | Near real-time |

**Ingestion path**:
```
Event Source -> Hono API Gateway -> Redis Stream (buffer) -> BullMQ Worker -> PostgreSQL
                                                         -> ClickHouse (Phase 3+, analytics copy)
```

Redis Streams act as a buffer to handle bursts. BullMQ workers process events asynchronously, enriching them (e.g., resolving customer identity from phone number) before writing to PostgreSQL.

**Why not write directly to PostgreSQL?** Because behavioral events are high-volume and bursty. A merchant with 500 daily catalog visitors generates thousands of events. Writing each one synchronously to PostgreSQL would create latency spikes. Redis Streams absorb the burst, and BullMQ workers drain it at a controlled rate.

#### Stream 2: Transactional Data (Medium Volume, Consistency-Critical)

This is order and payment data. It must be consistent and durable — losing a payment record is unacceptable.

| Event | Source | Volume | Latency Requirement |
|---|---|---|---|
| Order created | Customer PWA checkout | Low-Medium | Synchronous (must confirm) |
| Payment screenshot uploaded | Customer PWA | Low-Medium | Synchronous |
| Payment verified (OCR) | Finance Agent | Low-Medium | < 30 seconds |
| Payment confirmed (manual) | Merchant PWA | Low | Synchronous |
| Inventory adjustment | Merchant PWA or auto | Low-Medium | Synchronous |

**Ingestion path**:
```
Event Source -> Hono API Gateway -> Temporal Workflow -> PostgreSQL (within transaction)
                                                     -> Redis (cache invalidation)
                                                     -> Event Bus (notify agents)
```

Transactional data goes through Temporal workflows, not BullMQ. This is because:
- Temporal guarantees exactly-once execution
- If the server crashes after writing the order but before updating inventory, Temporal replays and completes both
- The Saga pattern handles compensation: if payment verification fails, the order status rolls back automatically

#### Stream 3: Imported Data (Batch, One-Time or Periodic)

This is data the merchant brings from external sources: Excel files, Google Sheets, other systems.

| Source | Data Type | Volume | Frequency |
|---|---|---|---|
| Excel/CSV upload | Products, customers, inventory | Hundreds to thousands of rows | One-time (onboarding) or periodic |
| Google Sheets (via MCP) | Products, customers, sales history | Hundreds to thousands of rows | One-time or periodic sync |
| Treinta export | Sales history, customer list | Hundreds of rows | One-time (migration) |
| Manual entry | Individual products/customers | One at a time | Ongoing |

**Ingestion path**:
```
File Upload / MCP Connection -> Import Service -> Validation Pipeline -> Staging Tables
                                                                     -> Merchant Review UI
                                                                     -> Approved -> Production Tables
```

This stream is detailed in Section 3 below.

### 2.2 Event Schema (Unified)

All events, regardless of stream, are normalized into a unified schema before storage:

```typescript
interface NovaEvent {
  id: string;                    // UUID v7 (time-sortable)
  tenant_id: string;             // Merchant UUID (multi-tenant key)
  event_type: string;            // e.g., "catalog.product_viewed", "order.created"
  entity_type: string;           // e.g., "customer", "product", "order"
  entity_id: string;             // UUID of the entity
  actor_type: "customer" | "merchant" | "system" | "agent";
  actor_id: string;              // UUID of who/what triggered the event
  data: Record<string, unknown>; // Event-specific payload
  metadata: {
    source: string;              // "pwa_customer", "pwa_merchant", "whatsapp", "import", "agent"
    ip?: string;                 // Hashed, for geo approximation only
    user_agent?: string;         // For device detection
    session_id?: string;         // For session grouping
  };
  created_at: Date;              // Event timestamp
}
```

This unified schema means that every interaction — whether a catalog visit, a WhatsApp message, a payment, or an AI agent action — is stored in the same format. This makes it trivial for agents to query across all data types.

### 2.3 Data Flow for Agent Consumption

The agents don't query raw events. They consume **materialized views** that are pre-computed and kept up-to-date:

```
Raw Events (PostgreSQL) -> Materialized Views (PostgreSQL) -> Agent Knowledge (pgvector)
                        -> Redis Cache (hot data)
```

Key materialized views:

| View | Contents | Refresh Rate |
|---|---|---|
| `customer_profile` | Full customer card with all computed fields | Real-time (trigger-based) |
| `customer_rfm_scores` | RFM scores per customer | Hourly (BullMQ cron job) |
| `customer_segments` | Segment assignments per customer | Hourly |
| `product_performance` | Sales velocity, margin, view-to-purchase ratio per product | Every 15 minutes |
| `daily_financials` | Income, expenses, margin, cash flow per day | Real-time (trigger-based) |
| `accounts_receivable` | Pending payments with aging | Real-time (trigger-based) |
| `catalog_analytics` | Page views, unique visitors, top products per day | Every 15 minutes |

## 3. Migration Pipeline: From Chaos to Clean Data

### 3.1 The Onboarding Philosophy

The merchant's first experience with Nova must follow this sequence:

```
1. SIGN UP (phone + Clerk auth, 30 seconds)
2. CREATE STORE (name, logo, category, 2 minutes)
3. IMPORT OR CREATE (the critical fork)
   ├── "I have data" -> MIGRATION PIPELINE
   │   ├── Upload Excel/CSV
   │   ├── Connect Google Sheets
   │   └── Manual paste
   └── "I'm starting fresh" -> GUIDED CREATION
       ├── Add first product (photo + AI)
       ├── Share catalog link
       └── First sale
4. CONFIGURE PAYMENTS (Pago Movil data, Zelle data)
5. START SELLING
```

The migration pipeline is step 3A. It must be **forgiving, visual, and fast**. The merchant is not a data engineer. They have a messy Excel file with inconsistent columns, duplicate rows, and mixed formats. Nova must handle this gracefully.

### 3.2 Migration Pipeline Architecture

### 3.3 Step-by-Step: Product Import

**Step 1: Upload**

The merchant uploads a file or connects a Google Sheet. Supported formats:
- `.xlsx` (Excel)
- `.csv` (comma, semicolon, or tab separated)
- `.tsv`
- Google Sheets (via MCP, live connection)
- Copy/paste from any table (clipboard parsing)

**Step 2: Parse & Detect**

The Import Service uses AI (Claude Haiku, fast and cheap) to:
- Detect column meanings from headers and sample data
- Map merchant columns to Nova fields

Example: The merchant's Excel has columns "Producto", "Precio Bs", "Precio $", "Cantidad", "Foto URL". The AI maps:
- "Producto" -> `product.name`
- "Precio Bs" -> `product.price_bs`
- "Precio $" -> `product.price_usd`
- "Cantidad" -> `product.stock`
- "Foto URL" -> `product.image_url`

The merchant sees a visual mapping screen:

```
YOUR COLUMN          →    NOVA FIELD
─────────────────────────────────────
Producto             →    Product Name ✓
Precio Bs            →    Price (Bs) ✓
Precio $             →    Price (USD) ✓
Cantidad             →    Stock ✓
Foto URL             →    Image URL ✓
Categoria            →    Category ✓ (new: will be created)
Descripcion          →    Description ✓
Codigo               →    SKU ✓
[Unmapped: "Notas"]  →    [Select field ▼] or [Skip]
```

The merchant can adjust any mapping with a tap. Unmapped columns can be assigned or skipped.

**Step 3: Validate & Clean**

The system runs validation rules on every row:

| Rule | Action | Example |
|---|---|---|
| Duplicate detection | Flag, suggest merge | Two rows with "Camisa Polo Azul" |
| Price format normalization | Auto-fix | "45,00" -> 45.00, "$45" -> 45.00 |
| Missing required fields | Flag for review | Product without name |
| Image URL validation | Check if accessible | Broken Google Drive links |
| Category normalization | Suggest existing or create new | "Zapatos", "zapatos", "ZAPATOS" -> "Zapatos" |
| Phone number normalization | Format to E.164 | "0414-1234567" -> "+584141234567" |
| Encoding fix | Auto-fix | "CamisÃ³n" -> "Camisón" |

**Step 4: Review & Approve**

The merchant sees a clean preview of what will be imported:

```
IMPORT PREVIEW: 47 products

✓ 42 products ready to import
⚠ 3 products need review (duplicate names)
✗ 2 products have errors (missing price)

[Review issues] [Import 42 ready now] [Fix all and import]
```

For issues, the merchant sees a simple editor:

```
⚠ DUPLICATE: "Camisa Polo" appears twice
  Row 12: Camisa Polo - $15 - Stock: 10
  Row 34: Camisa Polo - $15 - Stock: 5
  [Merge (stock: 15)] [Keep both] [Delete one]
```

**Step 5: Import to Production**

Once approved, the import runs as a Temporal workflow:
1. Write all products to a staging table (atomic transaction)
2. Validate foreign keys and constraints
3. If all pass: promote staging to production (atomic swap)
4. If any fail: rollback entirely, show errors
5. Trigger Image AI processing for any products with photos
6. Update search index (pgvector embeddings for product names/descriptions)

### 3.4 Customer Import

Customer import follows the same pipeline but with additional intelligence:

- **Phone number matching**: If a customer in the import matches an existing customer by phone number, the system suggests merging instead of creating a duplicate.
- **WhatsApp validation**: The system can check if imported phone numbers are valid WhatsApp numbers (via the WhatsApp Business API's contact check endpoint).
- **Enrichment**: If the merchant imports just names and phones, the system creates minimal profiles. As customers interact with the catalog, profiles are enriched automatically.

### 3.5 Google Sheets Live Sync

For merchants who want to keep using Google Sheets alongside Nova (common during transition), the MCP integration supports bidirectional sync:

```
Google Sheets <--MCP--> Nova Import Service <--> PostgreSQL
```

- **Pull mode**: Nova reads from Google Sheets on a schedule (every 15 min) or on-demand
- **Push mode**: Nova writes back to Google Sheets when products/inventory change
- **Conflict resolution**: Nova is the source of truth. If both sides change, Nova's version wins (with notification to merchant)

This sync is a **transition tool**, not a permanent architecture. The goal is to get the merchant comfortable enough to stop using Google Sheets entirely.

## 4. Proactive Intelligence System

### 4.1 The Five Intelligence Loops

Nova runs five continuous intelligence loops. Each loop observes data, detects patterns, and generates actions.

#### Loop 1: Customer Lifecycle Intelligence

**What it monitors**: Customer purchase patterns, visit frequency, engagement trends.

**What it detects and acts on**:

| Signal | Detection Logic | Action |
|---|---|---|
| **Repeat visitor, no purchase** | 3+ catalog visits in 7 days, 0 orders | Suggest first-purchase incentive |
| **Cart abandonment** | Item added to cart, no checkout in 2 hours | Send WhatsApp reminder with cart contents |
| **Purchase cycle deviation** | Customer's average cycle is 12 days, now at 18 days | Flag as "At Risk", suggest win-back message |
| **VIP promotion** | Customer crosses VIP threshold (auto-calculated) | Send congratulations + exclusive offer |
| **Churn prediction** | No visit or purchase in 2x average cycle | Move to "Hibernating", suggest deep discount |
| **Referral detection** | New customer arrived via shared catalog link from existing customer | Notify merchant, suggest rewarding referrer |

#### Loop 2: Inventory Intelligence

**What it monitors**: Stock levels, sales velocity, product performance.

**What it detects and acts on**:

| Signal | Detection Logic | Action |
|---|---|---|
| **Low stock alert** | Current stock < 7 days of sales velocity | Push notification to merchant |
| **Dead stock** | 0 sales in 30 days, stock > 0 | Suggest discount or promotion |
| **Trending product** | Sales velocity increased 50%+ in last 7 days | Suggest restocking, feature in catalog |
| **Seasonal pattern** | Same product spiked in same period last year | Pre-alert to stock up |
| **Margin alert** | Product margin dropped below merchant's average | Alert with suggestion to adjust price |

#### Loop 3: Financial Intelligence

**What it monitors**: Revenue, expenses, margins, cash flow, receivables.

**What it detects and acts on**:

| Signal | Detection Logic | Action |
|---|---|---|
| **Daily summary** | End of business day | Generate financial briefing |
| **Receivable aging** | Payment pending > 3 days | Suggest sending reminder |
| **Margin erosion** | Weekly margin trending down | Alert with product-level breakdown |
| **Revenue anomaly** | Today's revenue is 30%+ below same-day-of-week average | Alert: "Sales are slower than usual today" |
| **Exchange rate impact** | BCV rate changed > 2% | Suggest price update with preview |
| **Cash flow projection** | Based on receivables + historical patterns | "You'll have ~$X available in 7 days" |

#### Loop 4: Content Intelligence

**What it monitors**: Catalog engagement, social media performance (if connected), content freshness.

**What it detects and acts on**:

| Signal | Detection Logic | Action |
|---|---|---|
| **Stale catalog** | No new products added in 14 days | Suggest adding new products or refreshing photos |
| **High-engagement product** | Product with most views but low conversion | Suggest price adjustment or better description |
| **Content opportunity** | Product with high stock + good margin + no recent promotion | Generate ready-to-post Story/content |
| **Best posting time** | Analysis of when catalog gets most traffic | Suggest optimal time to share new content |

#### Loop 5: Operational Intelligence

**What it monitors**: Merchant behavior, system usage, onboarding progress.

**What it detects and acts on**:

| Signal | Detection Logic | Action |
|---|---|---|
| **Onboarding stall** | Merchant signed up but hasn't added products in 48h | Send helpful nudge with tutorial |
| **Feature discovery** | Merchant hasn't used CRM features after 2 weeks | Contextual tip: "Did you know you can see who visits your catalog?" |
| **Usage pattern** | Merchant always checks app at 8am | Schedule briefing delivery for 7:55am |
| **Support need** | Merchant navigating same screen repeatedly | Proactive: "Need help with this?" |

### 4.2 How Loops Execute

Each loop runs as a combination of:

1. **Real-time triggers** (Redis pub/sub): For events that need immediate response (cart abandonment, payment received)
2. **Scheduled jobs** (BullMQ cron): For periodic analysis (RFM recalculation every hour, daily briefing)
3. **Temporal workflows**: For multi-step actions (send campaign -> wait for responses -> analyze results -> adjust)

The Agno agents consume the outputs of these loops and decide which actions to surface to the merchant and which to execute autonomously (based on merchant's automation preferences).

## 5. Multi-Tenant Database Architecture

### 5.1 Strategy: Shared Database, Shared Schema, Row-Level Security

Nova uses the **pool model**: all tenants share the same database and tables. Tenant isolation is enforced at two levels:

1. **Application level**: Every query includes `tenant_id` in the WHERE clause (enforced by Drizzle ORM middleware)
2. **Database level**: PostgreSQL Row-Level Security (RLS) as a safety net

**Why pool model (not schema-per-tenant or database-per-tenant)?**

| Model | Cost | Complexity | Isolation | Nova's Scale |
|---|---|---|---|---|
| Database per tenant | Very high | Very high | Maximum | Overkill for 25K merchants |
| Schema per tenant | High | High | Strong | Migration nightmare |
| **Shared + RLS** | **Low** | **Low** | **Strong (with RLS)** | **Perfect for 25K-100K merchants** |

At Nova's target scale (25,000-100,000 merchants), the pool model with RLS provides strong isolation at minimal cost. If a single merchant grows to enterprise scale, they can be migrated to a dedicated schema or database later.

### 5.2 Core Schema Design

```sql
-- Tenant (Merchant) table
CREATE TABLE tenants (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name VARCHAR(255) NOT NULL,
    slug VARCHAR(100) UNIQUE NOT NULL,  -- for public catalog URL
    owner_user_id VARCHAR(255) NOT NULL, -- Clerk user ID
    plan VARCHAR(50) DEFAULT 'free',
    status VARCHAR(50) DEFAULT 'active',
    settings JSONB DEFAULT '{}',
    created_at TIMESTAMPTZ DEFAULT now(),
    updated_at TIMESTAMPTZ DEFAULT now()
);

-- Every tenant-scoped table follows this pattern:
CREATE TABLE products (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
    name VARCHAR(500) NOT NULL,
    description TEXT,
    price_usd DECIMAL(12,2),
    price_bs DECIMAL(18,2),
    cost_usd DECIMAL(12,2),
    sku VARCHAR(100),
    category_id UUID REFERENCES categories(id),
    stock INTEGER DEFAULT 0,
    status VARCHAR(50) DEFAULT 'active',
    images JSONB DEFAULT '[]',
    metadata JSONB DEFAULT '{}',
    embedding vector(1536),  -- pgvector for semantic search
    created_at TIMESTAMPTZ DEFAULT now(),
    updated_at TIMESTAMPTZ DEFAULT now()
);

-- Index on tenant_id is CRITICAL for performance
CREATE INDEX idx_products_tenant ON products(tenant_id);
CREATE INDEX idx_products_tenant_status ON products(tenant_id, status);

-- Row-Level Security
ALTER TABLE products ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON products
    USING (tenant_id = current_setting('app.current_tenant')::uuid);

CREATE POLICY tenant_insert ON products
    FOR INSERT
    WITH CHECK (tenant_id = current_setting('app.current_tenant')::uuid);
```

### 5.3 Setting Tenant Context Per Request

Every API request goes through the Hono middleware that:

1. Extracts the authenticated user from Clerk
2. Looks up which tenant(s) the user belongs to
3. Sets the PostgreSQL session variable

```typescript
// Hono middleware (simplified)
app.use('*', async (c, next) => {
  const user = await clerk.verifyToken(c.req.header('Authorization'));
  const tenantId = await getTenantForUser(user.id);

  // Set PostgreSQL session variable for RLS
  await db.execute(sql`SET app.current_tenant = '${tenantId}'`);

  c.set('tenantId', tenantId);
  await next();
});
```

With Drizzle ORM, every query automatically includes the tenant filter:

```typescript
// Drizzle query — RLS enforces tenant isolation at DB level,
// but we also filter explicitly for clarity and defense-in-depth
const products = await db
  .select()
  .from(productsTable)
  .where(eq(productsTable.tenant_id, tenantId));
```

### 5.4 Multi-User Per Tenant

A single merchant (tenant) can have multiple users:

```sql
CREATE TABLE tenant_members (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
    user_id VARCHAR(255) NOT NULL,  -- Clerk user ID
    role VARCHAR(50) NOT NULL DEFAULT 'member',
    -- roles: 'owner', 'admin', 'member', 'viewer'
    permissions JSONB DEFAULT '{}',
    created_at TIMESTAMPTZ DEFAULT now()
);

CREATE UNIQUE INDEX idx_tenant_members_unique ON tenant_members(tenant_id, user_id);
```

Roles and permissions:

| Role | Can sell | Can edit products | Can see finances | Can manage users | Can configure |
|---|---|---|---|---|---|
| **Owner** | Yes | Yes | Yes | Yes | Yes |
| **Admin** | Yes | Yes | Yes | Yes | No |
| **Member** | Yes | Yes | No | No | No |
| **Viewer** | No | No | View only | No | No |

This supports the common Venezuelan pattern where the owner has 1-2 employees who help manage the store.

### 5.5 Data Isolation Guarantees

| Layer | Mechanism | What It Prevents |
|---|---|---|
| **API Gateway** | Clerk auth + tenant lookup | Unauthenticated access |
| **Application** | Drizzle middleware adds tenant_id to every query | Accidental cross-tenant queries |
| **Database** | PostgreSQL RLS policies | Bugs in application code leaking data |
| **Storage** | Cloudflare R2 prefix-per-tenant | Image/file cross-access |
| **Cache** | Redis key prefix with tenant_id | Cache poisoning across tenants |
| **Agents** | Agno agent context includes tenant_id | Agent actions scoped to tenant |

Three layers of defense. If any one layer fails, the other two still prevent data leakage.

## 7. Is This Too Much? Scope Viability Analysis

### 7.1 The Honest Assessment

The full feature set described across both documents is ambitious. Here is a frank analysis of whether it's viable as a single product:

**The concern**: "This looks like a CRM + ecommerce + POS + accounting + marketing automation + AI platform all in one. Isn't that too much?"

**The answer**: It is a lot — but it's viable because of three architectural decisions:

#### Decision 1: Everything is a consequence of the sale

The merchant doesn't "use" 10 different modules. They do ONE thing: **sell**. Everything else is a consequence:

```
Merchant adds product (photo + AI) ──> Catalog exists
Customer visits catalog ──> Behavioral data captured (CRM feeds)
Customer orders via WhatsApp ──> Order created (inventory adjusts)
Customer pays via Pago Movil ──> Payment recorded (finances update)
System detects pattern ──> Suggestion appears (AI acts)
```

The merchant's conscious workflow is: **add product -> share link -> confirm order -> verify payment**. That's 4 actions. Everything else (CRM, analytics, suggestions, content) happens automatically in the background.

#### Decision 2: Progressive disclosure

The merchant never sees all 10 modules at once. The interface reveals complexity gradually:

- **Week 1**: They see Catalog + Orders + Payments. That's it.
- **Week 2**: After 10+ customers interact, the CRM tab appears with "You have 3 returning customers!"
- **Week 3**: After 20+ sales, the Finance tab appears with "You've earned $X this month"
- **Week 4**: After patterns emerge, the AI suggestions start appearing in the feed

This is the same pattern Shopify uses: start simple, reveal power as the merchant grows.

#### Decision 3: The agent layer absorbs complexity

Without AI agents, the merchant would need to:
1. Check their CRM manually
2. Decide who to message
3. Write the message
4. Send it
5. Check inventory
6. Update prices
7. Create content
8. Post on social media

With agents, the merchant sees: "Maria hasn't bought in 15 days. Send her a 5% coupon? [Yes] [No]". One tap replaces steps 1-4.

The agents are what make the scope viable. Without them, it would indeed be too much.

### 7.2 What to Cut If Needed

If development resources are constrained, here's the priority order (cut from bottom):

| Priority | Module | Cut Impact |
|---|---|---|
| 1 (MUST) | Catalog + Image AI | Without this, no product |
| 2 (MUST) | Checkout + Payments (Pago Movil) | Without this, no revenue |
| 3 (MUST) | Basic Inventory | Without this, overselling |
| 4 (SHOULD) | Micro-CRM (auto profiles) | Differentiator, but can launch without |
| 5 (SHOULD) | Import Pipeline | Important for onboarding, can be manual initially |
| 6 (SHOULD) | Financial Dashboard | High value, but can be Phase 2 |
| 7 (NICE) | AI Command Center | Differentiator, but can be Phase 2 |
| 8 (NICE) | WhatsApp Business API | Can use deep links initially |
| 9 (NICE) | Delivery Management | Can be Phase 3 |
| 10 (FUTURE) | Embedded Finance | Phase 4 |

The MVP (priorities 1-3) is achievable in 8-12 weeks. Adding priorities 4-6 extends to 16-24 weeks. The full vision is a 12-month roadmap.

### 7.3 Database Complexity Assessment

"Is the database design too complex for all this?"

No. The core schema is approximately 15-20 tables:

```
tenants, tenant_members,
products, categories, product_images,
customers, customer_events,
orders, order_items, payments,
inventory_movements,
campaigns, campaign_messages,
import_jobs, import_rows,
agent_memories, agent_actions
```

This is well within PostgreSQL's comfort zone. With proper indexing (especially on tenant_id) and RLS, this handles 100K+ merchants with millions of rows per table without issues.

The key performance considerations:
- **customer_events** will be the largest table (behavioral data). Partition by month.
- **pgvector embeddings** on products for semantic search. Separate index, HNSW for fast approximate search.
- **Materialized views** for pre-computed analytics. Refresh on schedule, not on every query.

| Company | What They Do | Revenue Model | Key Lesson for Nova |

### 8.2 Common Patterns Across All

1. **Start with workflow, not data**: The product solves a daily workflow problem first (selling, scheduling, ordering). Data collection is a side effect.

2. **Free or cheap entry, expensive exit**: The core tool is affordable. The data accumulated makes switching painful. The financial services on top are where the real money is.

3. **Mobile-first for field workers**: Every successful vertical SaaS for small businesses is mobile-first. Desktop is secondary.

4. **AI is the new moat**: Shopify Sidekick, Toast's underwriting models, HubSpot's predictive scoring — AI trained on proprietary data is the defensible advantage.

5. **Embedded finance is the endgame**: Toast, Shopify, Square, ServiceTitan — all generate more revenue from financial services than from software subscriptions. The software is the distribution channel for financial products.

### 8.3 What Nova Can Learn

The most important lesson from US companies: **don't try to be everything on day one**. Every company listed above started with ONE core workflow:

- Shopify: "Create an online store"
- Toast: "Take restaurant orders"
- HubSpot: "Track your contacts"
- Square: "Accept card payments"

Then they expanded outward from that core, always using data from the previous layer to power the next.

**Nova's core workflow**: "Take a photo, make it beautiful, share it, get paid."

Everything else — CRM, analytics, AI agents, financial services — grows from that seed. The architecture must support the full vision from day one (composable, multi-tenant, agent-native), but the product experience starts with that single, simple workflow.
